# 같은 프로젝트 경로에서 병렬 실행

작업 경로: `D:/WorkSpace/campus-major-tutoring-mvp`

기존 10단계·65개 명령은 완료 판정 기준으로 유지한다. 이 폴더는 역할별 배분과 병렬 준비 순서를 추가한다. YAML 자체를 터미널에서 실행하는 프로그램은 아니다.

## 파일과 역할

| 파일 | 담당 |
|---|---|
| `00-orchestration.yaml` | 병렬 준비 묶음·순차 통합·동시 실행 한도 |
| `A0-coordinator.yaml` | 총괄·선행 조건 확인·작업 배분·단계 판정 |
| `A1-contracts.yaml` | DB·API·이벤트 계약 |
| `A2-backend.yaml` | 회원·수업·협의·예약·운영 서버 |
| `A3-frontend.yaml` | 웹·사용자 흐름·화면 |
| `A4-billing.yaml` | 결제·보증금·환불·정산 |
| `A5-ai-data.yaml` | 추천·AI·분석 |
| `A6-qa.yaml` | 실제 통합 검증 |
| `A7-platform.yaml` | 초기 골격·의존성·CI·실행 환경 |

**총괄 1명 + 작업자 최대 3명**으로 운영한다. 8개 역할을 모두 상시 실행하는 것이 아니라 작업 묶음마다 필요한 역할을 배정한다. 실행 환경 한도가 더 낮으면 동시 작업 수를 줄인다. 역할 YAML은 원본 명령 ID를 참조하며 사업 요구사항을 중복 복사하지 않는다.

## 실행 방식

`선행 명령 완료 → 병렬 준비 → 준비 결과 수집 → 원본 순서대로 실제 연동·검증 → QA → 단계 판정`

S04에서는 백엔드·추천·웹 담당이 확정된 계약으로 동시에 준비한다. API가 아직 없으면 소비자는 자신의 범위에서 테스트 대역을 사용한다. 준비 보고는 `READY_FOR_INTEGRATION`이며 원본 명령의 `PASS`가 아니다. 준비 종료 후 S04-T01 → T02 → T03 순서로 실제 생산자·소비자를 연결하고, T04 QA와 GATE를 진행한다.

원본 `depends_on`과 완료 기준은 변경하지 않는다. 병렬 준비는 별도 보조 작업이다. 통합 담당자는 준비된 구현을 재사용하되 원본 프롬프트 전체와 완료 조건을 확인한다.

| 단계 | 병렬 준비 | 먼저 완료할 작업 |
|---|---|---|
| S01 | 기술 범위 + 인수 기준 초안 | 요구사항·정책 초안 |
| S02 | UX + 금액 계약 제안 + 추천 계약 제안 | 핵심 DB·API 초안 |
| S03 | 인증 서버 + 인증 화면 | 골격·스키마 |
| S04 | 회원/수업 서버 + 기본 추천 + 탐색 화면 | S03 통합 완료 |
| S05 | 협의/예약 서버 + 협의 화면 | 예약 스키마·금액 인터페이스 |
| S06 | 모의 결제 + 수업 운영 + 전체 화면 | 거래 스키마 |
| S07 | 결제 연동 + 예약 연동 + 결제 화면 | 제공자 사양·정책 확인 |
| S08 | 운영 로그 + 거래 대사 + 지표 분석 초안 | 실제 자료·분석 범위 확인 |
| S09 | AI 서비스 + 업무 연동 + AI 화면 | AI 계약·Python 골격 |
| S10 | 선택 트랙 역할만 최대 3명씩 | 확장 선택·계약 |

S07과 S09는 선행 게이트상 독립적이지만 웹·서버·설정을 공유한다. 같은 경로에서는 한 단계만 활성화한다. 외부 의존으로 단계가 대기하면 작업자를 모두 회수하고 결과를 저장한 뒤, 사용자가 허용한 범위에서 실행 가능한 다른 단계로 전환한다.

## 총괄에게 전달할 시작 프롬프트

아래는 **S01만 실행**하는 예다. 실제 개발을 시작할 때 전달한다.

```text
작업 경로는 D:/WorkSpace/campus-major-tutoring-mvp야.
agent-prompts/00-workflow.yaml,
agent-prompts/parallel/00-orchestration.yaml,
agent-prompts/parallel/A0-coordinator.yaml을 읽어줘.

이번 실행 범위는 S01이야. 총괄 1명과 작업자 최대 3명을 사용해줘.
steps 순서대로 준비 작업을 병렬 배분하고,
원본 명령의 depends_on과 완료 기준을 그대로 지켜줘.
준비 보고서를 원본 명령의 PASS로 취급하지 말고,
실제 통합·검증 결과를 원본 handoff_file에 기록해줘.
S01-GATE까지 처리한 뒤 결과와 다음 실행 가능한 단계를 보고해줘.
다음 단계는 자동 시작하지 말아줘.
```

더 진행하려면 범위를 `S01~S06`처럼 명시한다. 단계는 순서대로, 준비 묶음은 병렬로 진행한다. S07은 제공자 환경, S08은 실제 파일럿 기록이 필요하다. 없는 입력을 가짜로 채워 통과시키지 않는다.

## 역할별로 직접 전달하는 예

A0가 먼저 run_id·명령 ID·계약 버전·쓰기 범위를 배정해야 한다.

```text
작업 경로는 D:/WorkSpace/campus-major-tutoring-mvp야.
agent-prompts/parallel/00-orchestration.yaml과
agent-prompts/parallel/A3-frontend.yaml을 읽어줘.
A0가 배정한 run_id와 계약 버전으로 S04-T03의 prepare만 수행해줘.
원본 allowed_paths 안에서 화면과 계약 기반 테스트 대역을 준비하고,
백엔드 연동이 아직 없으면 READY_FOR_INTEGRATION으로 보고해줘.
원본 handoff_file에 PASS를 쓰거나 다음 명령을 시작하지 말아줘.
```

## 같은 경로의 충돌 방지

- A1만 공통 계약·migration을 수정하고 A7만 설치·lockfile·루트 설정을 수정한다. 이런 변경은 다른 쓰기 작업이 멈춘 상태에서 진행한다.
- A2의 서버 범위에서 billing과 recommendations를 제외한다. 공통 서버 조립은 A2에게 변경 요청한다. A5의 AI worker는 `services/ai/**`, A2의 업무 worker는 `apps/worker/src/**`다.
- 같은 역할에는 동시에 한 작업만 준다. 파일 소유권만으로 실행 자원이 자동 격리된다고 가정하지 않는다.
- 공유 DB의 migration/reset/seed, 의존성 설치·코드 생성은 단독 실행한다. 테스트 DB/schema·포트·임시 출력 경로를 분리할 수 있을 때만 해당 검증을 병렬 실행한다.
- `.next`, `dist`, `coverage`, 공용 fixture와 생성 타입도 공유 출력이다. 격리되지 않은 전체 빌드·통합 테스트는 쓰기 작업을 모두 종료한 후 순차로 실행한다.
- 계약 변경 시 관련 준비 작업을 회수하고 새 계약 버전으로 다시 확인한다. 다른 사람의 미완성 파일을 실제 API 계약으로 삼지 않는다.
- 준비 실패를 PASS로 바꾸지 않는다. 독립 작업은 마무리할 수 있지만 차단된 통합은 해결 후 진행한다.

## 결과 기록

- 준비 보고서: `docs/parallel-preparation/<run_id>/<command_id>.md`
- 총괄 배분 기록: `docs/product/parallel-runs/<run_id>.md`
- 실제 완료: 기존 `docs/handoffs/Sxx-Txx.md`와 단계 보고서 경로

재실행 시 새로운 run_id로 입력·파일 해시·검증·재사용 결과를 기록한다. 준비 중에는 다른 담당자의 보고서와 원본 완료 보고서를 수정하지 않는다.

`validate-parallel.cjs`는 원본 65개 명령의 통합 순서, 역할 참조, 최대 3개 동시 준비, 독점 작업 분리, 파일 해시를 검사한다. 실제 에이전트 실행기는 아니다.
